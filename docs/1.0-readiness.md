# 1.0 readiness

Dovecote is currently pre-1.0 (`0.2.0`). This page is the short release
checklist for deciding when the storage contract is ready to become a stable
Rust API. It records evidence to collect; it does not promise that an
environment-gated check passed merely because the repository contains it.

## Must-do gates

Before publishing 1.0, the release review must have:

- stable Rust and Rust 1.94 passing formatting, strict Clippy, tests, examples,
  and workspace rustdoc;
- the exact PostgreSQL, MySQL 8.4, MySQL Innovation, MariaDB, and SQLite
  backend matrix passing with the settings recorded in the
  [support matrix](support-matrix.md), including schema, locking, race,
  timestamp, error, and migration evidence;
- complete-history and rollback/reconciliation fixtures for the documented
  Keepsake/Gatekeep bridge, with historical migration bytes hash-checked;
- deterministic CloudEvents projection vectors and the pinned CloudEvents
  schema/SDK checks passing, plus a separately reviewed live CDC transform for
  any backend that will be advertised for CDC;
- package archives verified in the Dovecote-first publication order, a clean
  security-reporting route, and independent review of the code, durable schema,
  public API, and evidence; and
- an authored example that shows caller-owned transaction enqueue, schema
  checking, claim/fence handling, retry or acknowledgement, and bounded
  snapshot paging without presenting itself as a production worker.

The checked-in SQLite walkthrough is
[`crates/dovecote-sqlx-sqlite/examples/basic.rs`](../crates/dovecote-sqlx-sqlite/examples/basic.rs)
and runs with:

```sh
cargo run -p dovecote-sqlx-sqlite --example basic
```

All SQLx adapters now have tenant-scoped claim/page/operation boundaries and an
explicit administrative handle. Tenant support is a storage authority, not
authorization; applications still own identity, policy, and role assignment.
PostgreSQL RLS is optional and requires separate role review. MySQL/MariaDB
does not provide an adapter RLS profile: use a separate database for the
strongest isolation. SQLite's database file is the security boundary; use one
file per tenant where regulated isolation requires it.

## Explicit non-goals

1.0 does not add a worker supervisor, transport client, broker integration,
automatic migration runner, tenant authorization, FIFO ordering,
exactly-once publication, retention/deletion job, or status-query service.
Applications own transport policy, operational SQL, tenant boundaries, and
retention. Dovecote remains a storage contract with concrete SQLx adapters and
an application-owned transaction boundary.

## Version policy

| Contract | Policy |
| --- | --- |
| Rust API | The 0.x line permits intentional hardening with release notes. Capture the public API baseline at the 1.0 release candidate and enable semver/API-diff automation there; that automation must not block the remaining pre-1.0 hardening. |
| MSRV | Rust 1.94 remains the declared minimum. Stable and 1.94 are both required for release checks. After 1.0, an MSRV increase requires at least a minor release, a changelog entry, and evidence from both the previous and new toolchains. |
| SQLx and backends | Adapters use the pinned SQLx 0.9 line. Backend support is version-specific and only advertised with the exact matrix, settings, live evidence, and migration fixtures. |
| Durable schema | Each adapter's schema version 2 baseline and v1 migration artifacts are immutable release inputs. Changes are forward-only, application-run migrations with compatibility metadata, rollback/reconciliation evidence, and no startup migration. |
| CloudEvents projections | The wire target remains CloudEvents 1.0 with deterministic Dovecote output. The repository pins its 1.0.2 schema/fixture inputs; any byte or semantic change needs updated vectors, compatibility review, and binding evidence. |

This policy keeps semver, MSRV, SQLx/backend support, durable bytes, and wire
projections as separate decisions. A change in one contract does not silently
rewrite another.
